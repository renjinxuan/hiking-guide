## 一、产品概述

### 1.1 一句话定位

**徒步版的内容平台（徒步版小抖音）**：用 AI 把徒步风景照变成"高级 + 专业"的内容，沉淀成个人徒步图鉴，通过广场像抖音一样分发，社交靠内容吸引自然发生（不违规、不做跳转）。

**产品的完整逻辑（合伙人对内共识，务必遵循）**：

```
阶段一（工具，冷启动）：
  卖点 = AI 辅助标注（滤镜 + 地理知识）
  · 让图片更「高级」（更好看、更有力量感、适合晒图）
  · 让图片更「专业」（识别地貌、标注地理知识、涨知识）
  → 这是"让人愿意生产内容"的引擎

阶段二（内容平台，留存）：
  · 个人徒步图鉴 = 我的作品集（可积累、可回看）
  · 广场 = 刷徒步内容（像刷抖音）
  → 这是"让人愿意留下来"的引擎

阶段三（社交，自然发生，不违规）：
  · 用户看到同好 → 自发私下联系
  · 朋友圈分享 → 别人扫码/点进来 → 觉得平台好 → 留下
  → 我们不做违规跳转，只提供内容平台，社交是内容吸引的自然结果
```

> **核心洞察（最终版）**：产品是「徒步版的内容平台」，类似"徒步版小抖音"。工具（AI 滤镜+标注）负责生产内容，图鉴+广场负责分发和留存，社交是内容吸引的自然结果而非设计出来的功能。**不违规、不做跳转，护城河靠"内容 + 图鉴资产沉淀"。**

**产品 Slogan：让每一次徒步，都看懂脚下的山川。**

> 备选 slogan（供不同场景使用）：
>
> - 脚下的山川，值得被读懂（更文艺）
> - 拍照识地貌，徒步也涨知识（更功能向）
> - 读懂山川，从这里开始（极简）

### 1.1.1 竞争策略（关键定位，务必遵循）

- **不跟两步路/六只脚竞争路线记录、路线搜索、组队等重功能**（它们是成熟大产品）。
- **照片是主角，路线是配角**：路线仅作为「照片定位的底图」，为照片提供地图上的挂点。
- **核心差异化 = 照片精准定位到路线点 + AI 地理标注 + 个人徒步图鉴沉淀 + 内容广场分发**。
- **护城河（根本，已修正）**：**个人徒步图鉴/内容资产 + 内容平台**——用户每次徒步的标注照片累积成可回看的"作品集"，积累越多迁移成本越高；广场形成内容生态。这是两步路没有的（两步路是工具，不沉淀内容资产），且**不受微信平台能力限制**。
- **护城河（表层）**：AI 识图工具只回答"照片里是什么"，本产品回答「这张照片在你这条徒步路线的哪个点拍的」。
- **破冰/引流点**：用户分享"路线 + 标注照片"到朋友圈 → 引流进小程序 → 沉淀为自己的图鉴 → 浏览广场内容。
- 一句话：**做"徒步版的内容平台（小抖音）"，不做"第二个两步路"。**

> **重要（合规教训，务必牢记）**：微信小程序**没有"跳转加好友/建群"的 API**，且"展示微信号/二维码诱导加微信"是审核红线。**不做任何违规跳转**。社交靠"内容吸引 + 用户自发私下联系 + 合规的分享卡片"，而非平台引导跳转。

> 重要原则：用户要的是「照片 + AI 标注 + 成图 + 图鉴沉淀 + 广场内容」，不是「路线」。路线只是让照片"有个位置"的辅助信息。
> **主次关系（务必牢记）**：AI 标注是"获客钩子/入口"，「个人徒步图鉴 + 内容广场」是"根本价值/护城河"。社交是"内容吸引的自然结果"，不做设计、不做违规引导。

### 1.1.2 产品演进方向（天花板）

AI 标注只是起点，未来可演进为「**AI 一键成片**」：

```
现在（MVP）：照片 → AI 地理标注 → 静态成图 → 发朋友圈
    ↓ 演进（第二阶段，不做进 MVP）
未来：徒步照片合集 → AI 一键生成短视频
    · 自动套用抖音/视频号爆款模板
    · 自动配 BGM（户外感音乐）+ 自动生成文案
    · 自动加地理标注动画 + 字幕
    → 一键发视频号 / 抖音 / 朋友圈
```

> 重要：**AI 一键成片是第二阶段，明确不做进 MVP**。MVP 先把「照片标注 + 成图 + 微信社交」闭环跑通、验证，再上视频生成，避免 MVP 失控。

### 1.2 目标用户

业余徒步爱好者（核心）、户外/地理科普内容创作者（放大器）、自然教育/研学机构（长尾）。

### 1.3 MVP 范围（重要：只做这些，不做之外的功能）

MVP 只包含以下七个模块：

1. **用户登录**：微信一键登录
2. **照片拍摄与定位**（主角）：拍照/选图，照片带 GPS 定位，可挂到路线点（路线可选）
3. **AI 地理标注**（核心，投入最高优先级）：识别地貌 → 生成科普标注图 → 用户可编辑
4. **路线底图**（配角，可选）：简化记录轨迹 / 导入 GPX，仅为照片提供挂点底图
5. **成图分享**：标注照片 + 位置小图合成，一键保存/发朋友圈
6. **个人徒步图鉴**（核心护城河）：标注照片累积成可回看的"我的图鉴/作品集" + 分享卡片 + 轻量广场 + 留言
7. **数据持久化**：照片/标注/路线/图鉴云端保存

> 核心主线（务必牢记）：**拍照 → AI 标注 → 成图分享 → 图鉴沉淀**。路线是可选配角，仅当用户需要"照片挂在某个位置"时才用到。

### 1.4 MVP 明确不做（避免 AI 过度开发）

- ❌ 复杂的社交关系链：关注/粉丝、私聊 IM、完整的好友系统
- ❌ 组队约伴的完整匹配（时间/人数/报名审批等重流程）——MVP 只做"路线广场 + 留言找搭子"的轻量形态
- ❌ 社区信息流推荐算法、点赞、评论（MVP 仅做简单留言）
- ❌ 跳转微信加好友/建群（微信无此 API 且违规）
- ❌ 领队认证、商业路线
- ❌ 多端（只做微信小程序，不做 H5/App）
- ❌ 后台管理系统（MVP 阶段不做管理后台）

> 注1：商业化（会员订阅 + 计费分层）已纳入 MVP，见第八章。
> 注2：「交友/找搭子」在 MVP 用**合规的轻量形态**（分享卡片 + 路线广场 + 简单留言）实现，不做完整社交关系链，也**不做违规的跳转加微信**。

## 二、核心差异化功能：AI 地理标注（详细定义）

### 2.0 两种标注模式（关键设计，务必实现）

用户拍照后，可**自由选择**标注模式（这是区别于所有 AI 识图工具的核心）：

| 模式 | 用户场景 | 用户要什么 | 产品给什么 | 是否用 AI |
| --- | --- | --- | --- | --- |
| **① 位置标注（轻）** | 拍自拍、拍人物、随手拍 | 只要"我在哪拍的" | 照片 + 地理位置 + 路线点小图 | ❌ 不用 AI，仅定位 |
| **② AI 地理标注（重）** | 拍地貌、山、峡谷、岩石 | 看懂地貌、涨知识 | 照片 + AI 地理科普标注 + 位置 | ✅ 用 AI |

**核心差异化（务必牢记）**：市面上 AI 识图工具只回答"照片里是什么"，而本产品回答「**这张照片是在你这条徒步路线的哪个点拍的**」——这是"路线 + 照片 + GPS 挂点"三者结合才有的能力，是纯识图工具做不到的护城河。

- 模式① 位置标注：免费、轻量、快，所有照片默认可用
- 模式② AI 地理标注：核心付费点，按会员分层（见第八章）

> 用户可对同一张照片在两种模式间切换。自拍、人物照默认走模式①；地貌、风景照用户可选模式②。

### 2.1 功能目标

用户对某张徒步照片点击「AI 标注」，系统调用大模型识别照片中的地理/地貌特征，生成一组"科普标注 + 专业术语"的组合，叠加渲染到照片上，用户可编辑后保存分享。若照片内容不适合地理标注（如自拍、人物），用户可改选「位置标注」模式，仅标注拍摄位置。

**AI 标注的两大核心价值（产品的获客卖点，务必围绕这两点设计）**：

1. **让图片更有「知识含量」**：识别地貌、标注地理知识，把普通照片变成"看懂山川"的科普图，这是内容上的价值。
2. **让图片更有「生命力/力量感」**：通过专业标注 + 高级视觉呈现，让照片更好看、更震撼、更有晒图欲，更方便发朋友圈。

> 这两点是产品的「入口钩子」，解决冷启动"没人"的问题。它本身不是终局（终局是社交约徒步），但它是把用户"吸引进来"的关键。

### 2.2 标注风格（关键，决定产品调性）

遵循「**科普为主，专业为辅**」：

- **主标注文案**：用通俗易懂的语言，面向大众（如"这里的山崖为什么是一层一层的？"）
- **副标签**：附带专业地理术语作为背书（如【沉积岩层理构造】）
- **标注形态**：带半透明深色背景的文字块 + 彩色箭头/框选/虚线，指向照片中的具体部位
- **参考风格**：类似地质/地理教科书里的地貌科普讲解图（见文末附录示例）

### 2.3 标注数据模型（AI 输出的 JSON 结构，务必按此约定）

AI 对每张图返回如下 JSON：

```json
{
  "summary": "一句话整体概述这张图的地貌特征",
  "annotations": [
    {
      "id": "a1",
      "type": "box",
      "x": 0.32,
      "y": 0.28,
      "w": 0.20,
      "h": 0.15,
      "angle": 45,
      "title": "为什么山崖是一层一层的？",
      "term": "沉积岩层理构造",
      "detail": "岩石按不同时期一层层堆积形成，颜色深浅代表不同成分的沉积层。",
      "color": "#3B82F6"
    }
  ]
}
```

**字段说明**：

|   |   |   |   |
| --- | --- | --- | --- |

- `type`：标注类型，`box`(框选) | `arrow`(箭头) | `line`(虚线) | `point`(点位)
- `x` / `y`：归一化坐标（0\~1，相对图片宽度/高度）
- `w` / `h`：仅 `box` 类型需要，归一化宽高
- `angle`：仅 `arrow` 类型需要，箭头朝向角度（0\~360）
- `title`：主标注（科普语言）
- `term`：副标签（专业术语），可为空字符串
- `detail`：详细解说（1\~2 句形成原理）
- `color`：标注颜色（十六进制）

**约束**：

- 坐标一律用归一化值（0\~1），前端按图片实际尺寸换算成像素，保证不同分辨率下位置正确。
- 每张图标注数量建议 2\~6 条，不宜过多。
- `term` 字段优先给专业术语，但不强制。

### 2.4 AI 标注流程（端到端）

```
用户点击「AI 标注」
  → 前端上传原图到云存储（Storage），拿图片路径
  → 前端调用云服务 LLM（多模态视觉模型），传入图片 + 地理标注 Prompt
  → 大模型流式返回 JSON 文本，前端累积后 JSON.parse
  → 校验 JSON 格式 → 写入照片表的 ai_annotation 字段
  → 前端渲染标注图层，用户可编辑
  → 用户确认后，前端将标注合成到图片上，生成最终图
```

### 2.5 用户编辑能力（关键设计）

- 可**拖动**任意标注的位置
- 可**增删**标注
- 可**修改**主标题、术语、详细文案
- 可切换标注颜色
- 编辑后重新保存，覆盖 `ai_annotation` 字段，并标记 `is_edited = true`

### 2.6 大模型提示词（Prompt）设计

地理标注分两套 Prompt，按会员等级选择（免费 = 科普版，会员 = 专业版）。

**科普版 system prompt（免费用户）**：

```
你是一位自然科普讲解员。请分析这张户外徒步照片，
识别其中常见的地理与地貌特征（如：山体、峡谷、河流、植被、岩石等）。
对每个识别到的特征：
1. 用通俗易懂、有亲和力的中文写一句"主标注"（面向大众，可带趣味提问）
2. 给出对应的专业地理术语（副标签，作为科普小知识）
3. 用 1 句简单解释它是什么
4. 给出该特征在照片中的归一化坐标和标注类型
输出严格的 JSON，结构为：
{"summary": "...", "annotations": [{"id","type","x","y","w","h","angle","title","term","detail","color"}]}
只输出 JSON，不要输出其他内容。
```

**专业版 system prompt（会员用户）**：

```
你是一位资深地质/地貌学家。请对这张户外徒步照片进行专业的地貌学分析，
识别其中的地质构造与地貌成因（如：断层、岩石层理、V型谷、溯源冲沟、
洪积扇、喀斯特地貌、侵蚀地貌等）。
对每个识别到的特征：
1. 用准确的中文写一句"主标注"（专业表述，可含专业术语）
2. 给出对应的专业地理术语（副标签）
3. 用 2-3 句专业阐述其形成机制与地质背景
4. 给出该特征在照片中的归一化坐标和标注类型
输出严格的 JSON，结构为：
{"summary": "...", "annotations": [{"id","type","x","y","w","h","angle","title","term","detail","color"}]}
只输出 JSON，不要输出其他内容。
```

### 2.7 AI 标注模型选型（已确定，含免费/付费分层）

使用 WorkBuddy 云服务 LLM 的多模态模型，`supportsImages` 为 true 的模型。**按会员等级选择不同模型，实现免费/付费分层**：

| 等级 | 标注能力 | 模型 ID | 积分倍率 | 说明 |
| --- | --- | --- | --- | --- |
| 免费（科普） | 基础地貌识别（山/河/植被等），科普语言 | `glm-5.3-flash` | x0.08 | 低成本，效果好 |
| 会员（专业） | 深度地质/地貌标注（断层/层理/成因），专业术语 | `glm-5.3-flash`（专业版 Prompt）或 `deepseek-v4-pro` | x0.08\~x0.51 | 更强视觉/推理，配专业 Prompt |

> **实测结论（2026-10-30）**：用 `glm-5.3-flash` 实测两张真实地貌图，准确识别出「断层崖、沉积岩层理、V型谷、喀斯特溶蚀凹槽、溯源冲沟、洪积扇、侵蚀残柱」等专业地貌，效果达到专业版水准，且成本仅 x0.08。
> **注意**：`glm-4.6v` 在实测中调用报错（`maxAllowedSize` 仅 128KB，无法接收大图），**不要用 **`glm-4.6v`。改用 `glm-5.3-flash`（`maxAllowedSize` 1MB）。

**关键实现约束**：

- 调用时通过 `cloud.llm.models.list()` 读取实际可用模型，动态选择 `supportsImages === true` 且未 disabled 的模型，**不要硬编码模型 ID**（但优先 `glm-5.3-flash`）。
- 免费/付费的差异**不只是模型**，更核心是 **Prompt 的专业度**（见 2.8）：免费版用科普 Prompt，付费版用深度地质专家 Prompt。
- 每次标注调用前，需判断当前用户会员等级（见第八章），据此选择 Prompt。
- **图片必须压缩后再传入**：用户手机照片通常 2-5MB，base64 后更大，会超过模型 `maxAllowedSize`。前端上传前用 canvas 压缩到边长 ≤1280px、体积 ≤500KB。

### 2.8 免费/付费分层逻辑（核心变现点）

- **免费用户**：只能生成「科普版」标注（通俗语言、基础地貌），调用低成本模型
- **会员用户**：可生成「专业版」标注（专业术语、成因解析、更强模型）
- 用户点击「AI 标注」时，前端先判断会员状态：
  - 免费用户 → 走科普版 Prompt + 低成本模型
  - 会员用户 → 走专业版 Prompt + 专业模型（可选"科普/专业"两种模式切换）
- 免费用户尝试专业标注时 → 弹出升级会员引导（见第八章）

## 三、功能详细需求

### 3.1 模块一：用户登录（微信登录）

#### 3.1.1 功能点

- 进入小程序后，未登录时展示登录引导页
- 点击「微信登录」按钮，走微信小程序登录流程
- 登录成功建立 WorkBuddy 会话，后续所有数据操作自动携带身份
- 退出登录功能

#### 3.1.2 技术实现（务必按此）

- 使用 `wx.login` 获取 code，再调用云服务 SDK 的 `signInWithWechat(code, appid)`
- `appid` 通过 `wx.getAccountInfoSync().miniProgram.appId` 动态获取，**不要硬编码**
- 登录后通过 `cloud.auth.getSession()` 判断登录态
- 所有数据库/存储操作前，先做 Auth 门禁检查（见第五章）

### 3.2 模块二：照片拍摄、定位与标注模式选择（主角）

| 功能 | 说明 |
| --- | --- |
| 拍照/选图 | 两者都支持：小程序内相机拍照（保证拿到 GPS）+ 相册选图 |
| 照片定位（核心） | 照片带 GPS 坐标，可独立定位；若有路线，则挂到最近的轨迹点 |
| 标注模式选择（关键） | 拍照后让用户选：① 位置标注（轻，免费）② AI 地理标注（重，付费点） |
| 手动微调 | 照片位置允许用户手动拖动调整（GPS 可能漂移） |
| 照片时间轴 | 按拍摄时间浏览照片 |

> 重要提醒：微信小程序 `chooseImage` 从相册选图**默认可能不含 GPS 坐标**（隐私保护）。为保证定位，优先引导用户「徒步时用小程序内相机拍照」。相册选图作为补充（无坐标时靠时间戳估算或手动定位）。

#### 标注模式选择（核心交互，务必实现）

用户拍照/选图后，弹出模式选择：

- **位置标注**（默认，免费）：仅标注"我在哪拍的"——照片 + 地理位置文字 + 路线点小图，不用 AI，秒出结果
- **AI 地理标注**（付费点）：识别地貌，生成地理科普标注（见第二章 2.0）

> 自拍、人物照用户通常只需"位置标注"；地貌、风景照用户可选"AI 地理标注"。两种模式可随时切换。

#### 照片定位逻辑（核心算法）

1. 照片自带 GPS 坐标 → 直接定位，若有路线则找**最近的轨迹点**挂载。
2. 无 GPS → 用拍摄时间戳在路线起止时间内线性插值估算；无路线则仅靠手动定位。
3. 都失败 → 用户在地图上手动拖拽照片到某点。
4. 山区 GPS 可能漂移，**允许用户手动微调照片位置**。

> **关键**：照片定位**不依赖路线**。用户可以不记录任何路线，仅凭照片 GPS 坐标完成定位和成图。路线只是"让照片挂在一条轨迹上"的增强项。

### 3.3 模块三：路线底图（配角，可选）

| 功能 | 说明 |
| --- | --- |
| 简化轨迹记录（可选） | 徒步时点击「开始」，边走边记录轨迹点（经纬度、海拔、时间戳） |
| 边走边拍 | 记录过程中随时拍照，照片自动挂到当前轨迹点 |
| GPX 导入（可选入口） | 从两步路/六只脚导出 .gpx 导入，复用历史轨迹 |
| 路线信息编辑 | 名称、简介、难度（简单/中等/困难）、封面图 |
| 路线详情展示 | 轨迹地图、距离、累计爬升、总时长、照片挂点 |

> **关键定位**：路线是配角，仅为照片提供"挂在一条轨迹上"的底图。用户不记录路线也能完整使用核心功能（拍照 → 标注 → 成图）。

#### 后台定位技术难点（重要，需重点处理）

微信小程序在**锁屏/切后台**后，GPS 定位可能中断，导致轨迹断掉。需处理：

- 申请「持续后台定位」权限
- 用 `wx.startLocationUpdateBackground` 保持后台持续定位
- 锁屏/后台时继续记录轨迹点
- 断点补偿：恢复时补全丢失的轨迹段

> 若后台定位实在无法稳定，MVP 可降级为「前台记录为主」，但需在产品上如实提示用户"记录期间请保持小程序在前台"。

#### 两步路 GPX 导入链路（可选入口，非主路径）

```
两步路 App → 导出 GPX → 存手机文件 → 微信打开小程序 → 选择文件导入
```

> 此链路较绕，仅作为可选入口，不主推。

#### 轨迹数据存储格式

轨迹点以 JSON 数组存于 PostgreSQL 的 `jsonb` 字段，字段：`{ lat, lng, ele, time }`。

#### 路线指标计算

- 距离：相邻轨迹点球面距离累加（Haversine 公式）
- 累计爬升：相邻点正海拔差累加
- 总时长：末点时间 - 首点时间

## 五、技术方案（已确定，请按此实现）

### 5.1 总体架构

- **前端**：微信小程序原生（WXML + WXSS + JS），不用跨端框架
- **后端**：**WorkBuddy 云服务**（一个平台搞定数据库、登录、存储、AI）
- **地图**：微信内置 `map` 组件 + 腾讯位置服务（轨迹用 polyline 绘制）
- **AI**：云服务 LLM 的多模态模型（glm-5.3-flash 等，见 2.7）

### 5.2 云服务 SDK 接入（务必按此）

#### 5.2.1 安装与初始化

小程序使用 npm 包的 `/miniprogram` 子路径：

```bash
npm install @tencent-ai/workbuddy-cloud-sdk@dev
```

```js
// utils/cloud.js
const { createMiniProgramWorkBuddyCloud } = require('@tencent-ai/workbuddy-cloud-sdk/miniprogram')
const { createDiagnosticWx } = require('./workbuddy-cloud-diagnostics')

const cloud = createMiniProgramWorkBuddyCloud({
  endpoint: '<publicConfig.endpoint>',          // 必填，从云服务激活结果获取
  publishableKey: '<publicConfig.publishableKey>', // 必填
  workBuddyOAuthClientId: '<publicConfig.workBuddyOAuthClientId>', // WorkBuddy 账号登录时需要
  wx: createDiagnosticWx(wx),
})

module.exports = { cloud }
```

**关键约束**：

- `endpoint` 和 `publishableKey` 必须来自云服务激活返回的 `publicConfig`，**不要硬编码、不要从 env/位置推断**
- 小程序没有浏览器 runtime，**不要**用 `createWorkBuddyCloud`（根入口），必须用 `/miniprogram` 子路径的 `createMiniProgramWorkBuddyCloud`
- 不要把 SDK 的模块调用替换成手写的 `wx.request`

### 5.3 数据库设计（PostgreSQL，务必按此字段）

> 数据库由 `cloud.database` 访问，API 与 supabase-js 的 `from().select()...` 一致，返回 `{ data, error }`。所有用户表用 RLS 做数据隔离，`owner_id` 由 `DEFAULT auth.uid()` 自动填充，**前端不要手动传 owner\_****id**。

**routes（路线表）**

```
id BIGINT IDENTITY PRIMARY KEY
owner_id TEXT NOT NULL DEFAULT auth.uid()
name TEXT NOT NULL
description TEXT
difficulty SMALLINT               -- 1简单 | 2中等 | 3困难
is_public BOOLEAN DEFAULT false   -- 是否公开（决定是否出现在路线广场）
distance_km NUMERIC
elevation_gain_m NUMERIC
duration_min INTEGER
track_points JSONB                -- [{lat, lng, ele, time}, ...]
cover_photo_url TEXT
created_at TIMESTAMPTZ DEFAULT now()
updated_at TIMESTAMPTZ DEFAULT now()
```

**photos（照片表）**

```
id BIGINT IDENTITY PRIMARY KEY
owner_id TEXT NOT NULL DEFAULT auth.uid()
route_id BIGINT REFERENCES routes(id)   -- 可空，无路线时照片独立定位
storage_path TEXT                 -- 云存储中的路径
lat NUMERIC
lng NUMERIC
ele NUMERIC
taken_at TIMESTAMPTZ              -- 拍摄时间
annotation_mode SMALLINT          -- 1位置标注 | 2 AI地理标注（见 2.0）
location_label TEXT               -- 位置标注文案（逆地理编码出的地名，模式①用）

```

**posts（发布表，用于广场/交友找搭子）**

```
id BIGINT IDENTITY PRIMARY KEY
owner_id TEXT NOT NULL DEFAULT auth.uid()
route_id BIGINT REFERENCES routes(id)   -- 关联路线（可空，纯照片发布也行）
```

**RLS 策略（数据隔离，务必配置）**

- 每个用户表启用 RLS，`owner_id = auth.uid()` 才能读写自己的数据

- **posts / comments 特殊**：公开的 posts 允许所有登录用户读（`is_public = true`），但只有 owner 能写/改/删；comments 允许所有登录用户对公开 post 留言

### 5.7 AI 标注调用实现（LLM，多模态）

```js
// 1. 先读取可用模型，选 supportsImages 的模型（不要硬编码）
const models = await cloud.llm.models.list()
const model = models.find(m => m.supportsImages === true && m.disabled !== true)

// 2. 调用（注意：必须 stream: true，用 for await 收集完整文本）
let answer = ''
for await (const chunk of cloud.llm.chat.completions.create({
  model: model.id,
  messages: [
    { role: 'system', content: systemPrompt },  // 见 2.6
    { role: 'user', content: [
        { type: 'text', text: '请分析这张照片的地貌特征并输出标注 JSON' },
        { type: 'image_url', image_url: { url: imageUrl } }  // 图片地址
      ]
    },
  ],
  stream: true,
  response_format: { type: 'json_object' },
})) {
  const delta = chunk.choices[0]?.delta?.content
  if (delta) answer += delta
}
const annotation = JSON.parse(answer)
```

**关键约束**：

- 必须 `stream: true`（云服务 LLM 不支持非流式），用 `for await` 收集 delta 拼接完整文本再 parse
- 必须第一个 message 是 `system`（否则报错）
- 图片以 `type: 'image_url'` 传入，`url` 用云存储的签名 URL（或压缩后的 base64 data URL）
- 模型输出 JSON 用 `response_format: { type: 'json_object' }` 约束
- 对 `JSON.parse` 结果做格式校验，非法则重试或报错
- **图片必须先压缩**：用 canvas 压缩到边长 ≤1280px、体积 ≤500KB，否则可能超过模型 `maxAllowedSize` 报「请求参数无效」
- 优先用 `glm-5.3-flash`（实测效果好、maxAllowedSize 1MB）；`glm-4.6v` 实测报错不要用

### 5.8 地图合规（重要）

- 使用微信内置 `map` 组件 + 腾讯位置服务，**不自绘地图、不自建地图数据**。
- 轨迹点只用于个人记录与展示，符合《测绘法》相关要求。

## 六、视觉与交互规范

### 6.1 整体风格（已定：户外高级 + 浅色主 + 绿色品牌 + 暗色可选）

- **气质**：高级、克制、户外，类似苹果官网 / 始祖鸟 / Patagonia 的"少即是多"质感
- **默认浅色底**（户外强光可读性优先）：徒步场景多在户外强光下，深色底会反光、对比度下降、看不清，故**默认用浅色底**，参照两步路/六只脚等户外 App
- **绿色品牌色**：绿色 `#2E7D5B` 作为品牌主色（按钮/logo/强调），保留"山川绿意"的品牌辨识度
- **暗色模式可选**：提供深色模式（跟随系统或手动切换），给偏好深色/室内使用的用户，但**不设为默认**
- **大量留白 + 细线边框**（0.5px）+ 大字标题，保持苹果式高级感
- 字体：系统默认字体，重点用字号和字重区分（避免 600/700 粗体，用 400/500）

#### 配色方案（务必按此）

| 用途 | 颜色 |

### 6.2 AI 标注图视觉规范

- 标注文字块：深色半透明背景（约 75% 不透明度黑色）+ 白色文字
- 箭头/框选：高饱和彩色（绿 `#3FBF85`、金 `#D8A95A`、蓝、红），2\~3px 粗细
- **标注标签用"细边框小标签"风格**（像专业装备的规格铭牌），而非大色块
- 主标注字号大、术语字号小，形成层次
- 底部可加一句 summary 总述

### 6.3 交互原则

- AI 标注生成过程要有 loading 态和进度反馈
- 标注失败要有明确的错误提示和重试按钮
- 编辑标注时提供"撤销/重置为 AI 结果"选项

## 八、商业模式与计费（核心变现）

### 8.0 核心认知：盈利点不压在"AI 标注动作"上，而压在"成图结果"上

工具类产品有先天付费困境——用户对"工具动作"的付费意愿，远低于对"身份/面子/结果"的付费意愿。所以：

> **用户愿意掏钱的理由，不是"AI 花了算力"，而是"这张图让我晒出去更有面子、更好看、涨粉"。**

因此盈利点从"卖 AI 标注"转向"卖成图价值"。盈利分**前/中/后三期**（见 8.1）。

### 8.1 盈利模式：三层递进（前 / 中 / 后）

| 阶段 | 盈利点 | 具体内容 | 依赖前提 |
| --- | --- | --- | --- |
| **前期**（MVP 验证后） | **成图价值分层** | 高清导出、无水印、专业标注、专属模板、批量处理 | 用户量跑通 |
| **中期**（图鉴成型后） | **图鉴会员订阅** | 图鉴容量、图鉴美化/排版/导出成册、高清图鉴、云同步 | 用户开始积累图鉴 |
| **后期**（内容平台成型后） | **内容平台变现** | 广告（户外装备/旅行社/景区）、带货（徒步装备周边）、创作者抽佣、B 端（景区/研学定制科普内容） | 广场跑起来，成"徒步版小抖音" |

**一句话**：短期靠"成图质量分层"赚第一笔钱，中期靠"图鉴会员订阅"赚持续的钱，长期靠"内容平台广告 + 带货"赚大钱。

> ⚠️ **最该警惕的**：不要把盈利全押在"AI 标注按次收费"上——那是最弱、最容易被免费工具（豆包/通义识图）替代的一条路。盈利必须落在"结果"（成图、图鉴、平台）上，而非"动作"（标注）上。

### 8.2 收费分层（MVP 及后续的"成图价值"分层）

| 等级 | 能力 | 模型 | 价格（参考） |
| --- | --- | --- | --- |
| 免费 | 位置标注（免费、无 AI）+ 科普版 AI 标注（限量） | 无 / `glm-5.3-flash` | 0 元 |
| 会员 | 专业版 AI 标注 + 无限次 + 高清导出 + 无水印 + 专属模板 + 批量处理 | `glm-5.3-flash`（专业 Prompt）/ `deepseek-v4-pro` | 月卡/年卡（定价待定） |

> **转化钩子（重要）**：给每个新用户 **1-3 次免费的专业版 AI 标注体验**，让他先看到专业版的价值再引导付费。位置标注永远免费，作为留存的基础。
>
> **关键设计**：会员的价值不止"更专业的标注"，更在"成图质量的真实可感提升"（高清、无水印、模板、批量）——这才是用户愿意掏钱、且难以被免费工具替代的理由。

### 8.3 计费交互流程

```
用户点击「AI 标注」
  → 判断会员状态（查会员表 / 订阅状态）
  → 免费用户：默认走科普版；尝试专业标注时弹「升级会员」引导
      · 新用户有 1-3 次免费专业标注体验额度
  → 会员用户：可选「科普/专业」两种模式
  → 调对应模型 + 对应 Prompt 生成标注
```

### 8.4 数据需求（计费相关字段）

会员状态需持久化。建议在用户相关表增加会员字段：

```
会员/订阅表（或合并到用户表）
user_id TEXT          -- 关联 auth.uid()
plan SMALLINT         -- 0免费 | 1月卡 | 2年卡
expire_at TIMESTAMPTZ  -- 会员到期时间（null 表示未开通）
```

### 8.5 MVP 阶段的计费基调（重要：先免费跑通，验证用户量）

> **MVP 策略：先免费跑通、验证用户量为主，不一开始就做付费。** 付费分层是"跑通后再上"的事。

- **最小 MVP 阶段**：核心目标是验证"有没有人用、愿不愿意用"，**不做付费墙**。AI 标注先免费开放（或仅区分"科普/专业"两种模式，但不收费）。
- **验证通过后**：再引入 8.2 的"成图价值分层"收费（高清/无水印/专业标注/模板），先埋会员字段和分层逻辑，支付接入再延后。
- **支付环节（微信支付/虚拟支付）是明确的延后项**：先做"会员状态字段"的数据存储与判断，真实支付接入放在验证用户量之后。
- 若需接入微信虚拟支付，需满足微信侧资质（服务类目含"工具"、微信认证、ICP 备案等），需另行评估。

> 一句话：**先免费验证"有没有人用"，再付费验证"愿不愿意掏钱"**——顺序不能反。

## 九、给 AI 编码助手的实现指令（可直接照做）

1. 严格按照第三章功能范围和第五章技术方案实现，**不要添加 MVP 范围外的功能**。
2. 优先保证「AI 标注」链路完整可用，这是本项目最重要的功能。
3. 后端全部使用 WorkBuddy 云服务 SDK（`@tencent-ai/workbuddy-cloud-sdk/miniprogram`），**不要用 **`@cloudbase/js-sdk`**、不要手写 **`wx.request`** 对接云服务、不要自己搭服务器**。
4. AI 标注的 JSON 结构必须与 2.3 完全一致，前端渲染与后端校验都要基于此结构。
5. 数据库字段按 5.3 设计，务必配置 RLS 数据隔离，`owner_id` 用 `DEFAULT auth.uid()` 自动填充。
6. LLM 调用必须 `stream: true` + 首条 `system` message，图片用 `image_url` 传入，模型动态从 `models.list()` 选 `supportsImages` 的。
7. 地图用微信内置 map 组件，轨迹用 polyline 绘制。
8. 微信登录用 `wx.login` + `signInWithWechat(code, appid)`，`appid` 动态获取。
9. **实现免费/付费分层**：按会员状态选择科普版/专业版 Prompt 与模型（见 2.8 和第八章）；会员状态字段先做数据存储与判断，支付接入可延后。
10. 代码要分层清晰：页面 / 组件 / 工具函数 / 云服务封装，便于后续扩展组队等 Phase 2 功能。
11. 输出时给出：项目目录结构、每个页面/云服务封装的实现代码、数据库表结构 + RLS 配置说明、云服务初始化配置说明、部署运行步骤。
